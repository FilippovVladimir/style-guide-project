# Как участвовать в развитии руководства

Документ описывает, как предложить изменение в руководство по стилю, как
оформлять коммиты, как проходит ревью и как собрать сайт локально.

## Как предложить изменение

1. Если изменение спорное или крупное, сначала создайте Issue и опишите
   проблему: какой вопрос не решён в руководстве и какой вариант правила
   вы предлагаете.
2. Создайте ветку от актуальной `main`:

    ```bash
    git switch main
    git pull
    git switch -c docs/<краткое-описание>
    ```

    Префиксы веток: `docs/` — новые или изменённые правила,
    `fix/` — исправление ошибок, `ci/` — изменения проверок и публикации.

3. Внесите изменения, запустите проверки (раздел «Локальная сборка»).
4. Сделайте коммит по правилам Conventional Commits.
5. Отправьте ветку и создайте Pull Request в `main`, заполните шаблон
   описания.

## Требования к коммитам (Conventional Commits)

Формат сообщения:

```text
<тип>(<область>): <описание>

<тело — необязательно: что и зачем изменено>

<футер — необязательно: Refs #12, BREAKING CHANGE: ...>
```

Таблица 1 — Типы коммитов

| Тип | Когда использовать |
| --- | --- |
| `docs` | Добавлено или изменено правило, раздел, шаблон |
| `fix` | Исправлена ошибка, опечатка, неработающая ссылка |
| `feat` | Новая возможность сайта (поиск, плагин, тема) |
| `ci` | Изменены проверки или публикация в GitHub Actions |
| `build` | Изменены зависимости (`requirements.txt`) |
| `refactor` | Перестроена структура без изменения смысла правил |
| `chore` | Служебные изменения (`.gitignore` и т. п.) |

Правила:

- описание — на русском языке, со строчной буквы, без точки в конце,
  в повелительном наклонении: «добавить правила доступности»;
- длина первой строки — не более 72 символов;
- область — имя раздела латиницей: `style`, `formatting`, `content`,
  `templates`, `glossary`, `ci`;
- изменение, которое отменяет или меняет смысл существующего правила,
  помечайте `!` после типа и футером `BREAKING CHANGE:`.

Примеры:

```text
docs(style): добавить правила доступности текста
fix(formatting): исправить пример блока кода protobuf
ci: добавить проверку терминологии
docs(style)!: заменить «скачивание» на «загрузку»

BREAKING CHANGE: термин «скачивание» больше не допускается
```

## Процесс ревью

1. Каждый Pull Request проверяет минимум один участник, кроме автора.
2. Слияние возможно, только если проверки GitHub Actions прошли успешно.
3. Ревьюер проверяет:
    - соответствие изменения правилам руководства;
    - отсутствие противоречий с другими правилами;
    - наличие примеров «Так / Не так» у нового правила;
    - добавление раздела в навигацию и запись в журнале изменений.
4. Замечания оформляйте с идентификатором правила и предложением
   исправления. Используйте метки в начале комментария:
    - `[замечание]` — нужно исправить до слияния;
    - `[предложение]` — можно учесть или обсудить;
    - `[вопрос]` — нужен ответ автора.
5. Автор отвечает на каждый комментарий: исправляет и отмечает
   «Resolve conversation» или объясняет, почему не согласен.
6. После одобрения (Approve) автор выполняет слияние способом
   «Squash and merge» и удаляет ветку.
7. Публикация на GitHub Pages выполняется автоматически после слияния
   в `main`.

## Локальная сборка

Требования: Python 3.10+, Node.js 18+.

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
mkdocs serve                     # сайт откроется на http://127.0.0.1:8000
```

Проверки, которые выполняются в CI:

```bash
npx markdownlint-cli2
python scripts/check_terms.py docs
mkdocs build --strict
```

## Как добавить новый раздел

1. Создайте файл в подходящем каталоге `docs/`. Имя файла — латиницей
   через дефис: `docs/style/accessibility.md`.
2. Начните файл с заголовка первого уровня и вводного абзаца.
3. Оформите каждое правило заголовком второго уровня с идентификатором:
   `## ДС-1. Название правила`. Если раздел новый, выберите новый префикс
   и добавьте его в таблицу на странице `docs/index.md`.
4. Для каждого правила приведите примеры в таблице «Так | Не так».
5. Добавьте раздел в навигацию `mkdocs.yml` (блок `nav`).
6. Если появились новые термины, добавьте их в `docs/glossary.md`, а
   запрещённые варианты — в `scripts/check_terms.py`.
7. Добавьте запись в `docs/changelog.md`.
8. Запустите проверки и создайте Pull Request.
